

# SENTINEL Layer 4 Final Handoff / Knowledge-Transfer Audit

## 1. Project / Architecture Context

SENTINEL means **Semantic Execution Normalization and Translation Interface for Native Enterprise Legacy Environments**.

The repository implements this intended layered architecture:

```text
L1 Environment Drivers
        ↓
L2 State Reduction / Stability
        ↓
L3 Interaction Virtualization / Semantic Actions
        ↓
L4 Orchestration / Agent Boundary
        ↓
External AI Agent / MCP Client
```

### Layer responsibilities

- **L1** communicates with the target runtime.
- **L2** parses transport frames, reconstructs state, extracts fields, and determines stability.
- **L3** exposes semantic tools, validates actions, lowers actions, executes them, and produces L3 handoff payloads.
- **L4** owns runtime/session lifecycle, gateway ownership, action serialization, audit coordination, and the external agent boundary.
- **MCP** is a thin protocol adapter over L4.

The problem L4 solves is coordination. L1–L3 can connect, observe, validate, compile, and execute, but they do not own:

- Agent-facing lifecycle.
- Session ownership.
- Connection state.
- Concurrent agent calls.
- Clean startup/shutdown.
- Audit transaction boundaries.
- MCP exposure.

## Runtime-Agnostic Rule

`RuntimeOrchestrator` is intentionally runtime-agnostic.

It contains no branches for:

- TN3270.
- Hercules.
- MVS.
- TSO.
- ISPF.
- DOS.
- QEMU.
- ARM.
- GDB.

Runtime-specific behavior is hidden behind:

- `DriverRegistry`.
- `EnvironmentDriver`.
- `RuntimeSession`.
- Runtime-specific L1/L2 implementations.
- Future runtime-specific session adapters.

The existing `SessionBootstrapper` is target-specific and is not part of the generic `RuntimeOrchestrator` contract.

- One `RuntimeSession`.
- One active `AIToolGateway`.
- One active state reference.
- One driver reference.
- One action lock.
- One audit logger.

The generic session protocol is defined in `session.py:15`.

## C. Initial State Acquisition

`PipelineSession.initialize()` calls the existing stability engine:

```python
state, _ = await self.stability.wait_until_stable(...)
```

This is implemented in `session.py:35`.

The resulting `RuntimeState` is wrapped in `L2toL3HandoffPayload` and passed to `AIToolGateway`.

## D. L3 Gateway Ownership and Delegation

`RuntimeOrchestrator.connect()` uses:

```python

```

It does not rebuild:

- Driver.
- Reducer.
- Stability engine.
- Action lowerer.
- Dispatcher.

It creates the gateway using the dispatcher returned by the registry.

## E. Agent-Facing Operations

The public L4 API is:

```python
async def connect()
async def disconnect()

def is_connected()
def runtime_id()

def get_tools()
def get_observation()

async def execute_tool(name, arguments)
```

`get_observation()` and `get_tools()` delegate to `AIToolGateway`.

## F. Action Serialization

A per-orchestrator `asyncio.Lock` serializes mutating actions.

This prevents two calls from concurrently using the mutable `AIToolGateway.active_payload`.

Verified by:

- `test_mutating_actions_are_deterministically_serialized`

## G. Error Handling

L4 owns lifecycle-level errors:

- `RuntimeNotConnected`
- `InvalidRuntimeState`

L4 does not replace lower-layer validation errors.

Structured gateway results are returned unchanged.

Gateway exceptions are:

1. Audited.
2. Re-raised.

# 4. RuntimeOrchestrator

## Purpose

`RuntimeOrchestrator` owns one runtime session and exposes a stable L4 API to callers and MCP.

It coordinates existing lower layers. It does not implement their behavior.

## Lifecycle states

Defined in `orchestrator.py:15`:

```text
DISCONNECTED
CONNECTING
INITIALIZING
READY
EXECUTING
ERROR
DISCONNECTING
```

## Implemented lifecycle flow

```text
DISCONNECTED
    ↓ connect()
CONNECTING
    ↓ pipeline constructed and session connected
INITIALIZING
    ↓ initial RuntimeState acquired and gateway constructed
READY
    ↓ mutating execute_tool()
EXECUTING
    ↓ result or exception
READY
    ↓ disconnect()
DISCONNECTING
    ↓ teardown and disconnect
DISCONNECTED
```

## `connect()`

Defined at `orchestrator.py:58`.

Flow:

1. Require `DISCONNECTED`.
2. Set `CONNECTING`.
3. Call the configured pipeline factory.
4. Create a generic `RuntimeSession`.
5. Connect the session.
6. Set `INITIALIZING`.
7. Acquire initial state.
8. Create `L2toL3HandoffPayload`.
9. Construct `AIToolGateway`.
10. Set `READY`.

On exception, state becomes `ERROR` and the exception propagates.

## `disconnect()`

Defined at `orchestrator.py:83`.

Behavior:

- Safe when already disconnected.
- Acquires the action lock.
- Waits for an active action.
- Sets `DISCONNECTING`.
- Calls session teardown.
- Calls session disconnect.
- Clears owned state.
- Ends in `DISCONNECTED`.

## `is_connected()`

Returns true only when lifecycle state is `READY`.

## `runtime_id()`

Returns the underlying driver's `runtime_id`, if available.

## `get_tools()`

Delegates to:

```python
gateway.get_tools()
```

It requires a ready runtime.

## `get_observation()`

Delegates to:

```python
gateway.get_observation().to_dict()
```

It requires a ready runtime.

## `execute_tool()`

Defined at `orchestrator.py:111`.

For `get_screen_state`:

- Requires a ready gateway.
- Does not acquire the mutation lock.
- Delegates directly to the gateway.

For other tools:

1. Acquire per-instance lock.
2. Verify ready state.
3. Set `EXECUTING`.
4. Record audit start.
5. Delegate to `AIToolGateway.execute_tool()`.
6. Update active state.
7. Record audit completion.
8. Restore `READY`.
9. Release lock.

## No health method

There is no separate `health_check()` method on `RuntimeOrchestrator`. Health is represented by:

```python
is_connected()
```

The underlying driver has its own `health_check()` method, but L4 does not expose it currently.

# 5. Generic Session Abstraction

## `RuntimeSession`

Defined at `session.py:15`.

```python
class RuntimeSession(Protocol):
    async def connect()
    async def initialize() -> RuntimeState
    async def teardown(active_state)
    async def disconnect()
```

This is runtime-independent.

## `PipelineSession`

Defined at `session.py:35`.

It wraps an already-created L1/L2 pipeline:

- `EnvironmentDriver`
- `StateReducer`
- `StabilityEngine`

Behavior:

- `connect()` calls driver connect.
- `initialize()` waits for first stable state.
- `teardown()` is currently a no-op.
- `disconnect()` calls driver disconnect.

## `SessionBootstrapper`

Defined at `session.py:58`.

It contains target-specific behavior:

- TSO/ISPF assumptions.
- Username/password values.
- Logon text matching.
- AID key assumptions.
- Editable-field assumptions.
- ISPF exit behavior.
- LOGOFF behavior.
- Hardcoded generation numbers.

It is currently used by `LiveValidationHarness`, not by `RuntimeOrchestrator`.

## Why it must not move into `RuntimeOrchestrator`

Moving it into the orchestrator would violate the core L4 rule. The orchestrator must not know whether a runtime is:

- TN3270.
- Hercules.
- TSO.
- ISPF.
- DOS.
- QEMU.
- ARM.
- GDB.

A future target-specific adapter should implement `RuntimeSession` and encapsulate the bootstrap behavior:

```text
RuntimeOrchestrator
    ↓ generic RuntimeSession
Runtime-specific session adapter
    ↓
Driver / reducer / stability / bootstrap policy
```

## Current limitation

`PipelineSession.initialize()` only waits for the first stable state. It does not automatically execute `SessionBootstrapper.bootstrap()`.

Therefore, the generic orchestrator currently connects to the initial runtime screen, not automatically to the configured ISPF/TSO entrypoint.

# 8. Concurrency / Action Serialization

## Problem

`AIToolGateway.active_payload` is mutable.

Without serialization:

```text
Action A reads generation N
Action B reads generation N
Action A updates to N+1
Action B executes against stale state
```

## Current solution

Each `RuntimeOrchestrator` owns:

```python
self._action_lock = asyncio.Lock()
```

This is not global.

## Mutating actions

All tools except `get_screen_state` are treated as mutating for lock purposes.

This includes:

- `set_field_and_submit`
- `fill_form_and_submit`
- `trigger_action`

## Observation during execution

`get_screen_state` does not acquire the mutation lock, but it is rejected because the orchestrator is `EXECUTING`.

This avoids returning an intermediate mutable gateway state.

## Disconnect during action

`disconnect()` acquires the same lock.

Therefore:

1. Active action continues.
2. Action completes or raises.
3. Lock is released.
4. Disconnect proceeds.
5. Session teardown occurs.

No action is cancelled by L4.

## Failure recovery

After:

- Successful result.
- Structured failure.
- Gateway exception.
- Audit failure.

The orchestrator returns to `READY`, unless the lifecycle was changed externally.

# 15. Known Limitations

## Target-specific bootstrap/login

**Classification: SHOULD BE DONE BEFORE FINAL PROJECT**

`PipelineSession` only obtains the initial stable screen.

It does not invoke `SessionBootstrapper`.

The existing bootstrapper remains target-specific and is used by the validation harness.

## Reconnect/recovery

**Classification: FUTURE/STRETCH**

No automatic reconnect framework exists.

## Retry policy

**Classification: FUTURE/STRETCH**

No action retry policy exists.

## Idempotency

**Classification: FUTURE/STRETCH**

No idempotency keys or duplicate-action suppression exist.

## Multi-runtime registry

**Classification: FUTURE/STRETCH**

`DriverRegistry` creates a configured pipeline, but L4 does not maintain a registry of multiple active runtime sessions.

## Authentication/authorization

**Classification: SHOULD BE DONE BEFORE FINAL PROJECT**

MCP does not currently authenticate or authorize clients.

## Human confirmation

**Classification: FUTURE/STRETCH**

No approval mechanism exists for risky actions.

## Persistent audit storage

**Classification: SHOULD BE DONE BEFORE FINAL PROJECT**

Current audit logging is JSONL/file-based structured logging.

## Navigator/planning

**Classification: FUTURE/STRETCH**

Navigator integration exists in the legacy harness but is not part of `RuntimeOrchestrator` or the MCP adapter.

## QEMU/DOS/second runtime validation

**Classification: FUTURE/STRETCH**

Runtime-agnostic interfaces are tested with fake session implementations, but no second real runtime has been integrated.

## MCP dynamic tool exposure

**Classification: KNOWN LIMITATION**

The MCP adapter currently registers the known semantic tools explicitly.

It does not dynamically translate arbitrary schemas returned by `RuntimeOrchestrator.get_tools()`.

This is acceptable for the current MVP but should be revisited if L3 adds new tools.

## Live Claude write-path validation

**Classification: SHOULD BE DONE BEFORE FINAL PROJECT**

The direct Python L4 write path has been validated against Hercules.

The actual Claude Desktop → MCP → L4 → Hercules write path has not been validated.

## Shared live runtime test isolation

**Classification: SHOULD BE DONE BEFORE FINAL PROJECT**

Live Hercules tests mutate shared runtime state and should not run concurrently against one Hercules session.

# 16. What Not to Change

Future developers must not:

- Put TN3270 logic into `RuntimeOrchestrator`.
- Add Hercules-specific branches to L4.
- Add TSO/ISPF assumptions to generic `RuntimeSession`.
- Duplicate L3 validation.
- Duplicate generation-token checking.
- Bypass `AIToolGateway`.
- Bypass `ActionDispatcher`.
- Call `EnvironmentDriver` directly from the orchestrator.
- Move screen parsing into L4.
- Move stability logic into L4.
- Create a second action result model.
- Remove the per-orchestrator lock.
- Allow two mutating actions against one gateway concurrently.
- Cancel active runtime actions during disconnect.
- Make audit failures alter action behavior.
- Move the legacy harness into the production orchestration path.
- Put validation logic into MCP.
- Put retries or recovery into the MCP adapter.
